# @drivegolight/core

สูตรคำนวณเงินและภาษีทั้งหมดของ DriveGoLight! แยกออกมาเป็น TypeScript ล้วน
ไม่พึ่ง DOM ไม่พึ่งฐานข้อมูล ไม่พึ่งตัวแปร global ใด ๆ

**ทำไมต้องแยกออกมา** — เว็บ (Next.js) กับไฟล์ HTML แบบ offline ต้องใช้สูตรชุดเดียวกัน
ถ้าปล่อยให้มีสองชุด วันหนึ่งเลขภาษีจะไม่ตรงกันแล้วหาสาเหตุไม่เจอ นี่คือเหตุผลหลัก
ที่เลือกเขียน backend ด้วย TypeScript แทนที่จะแยกเป็น Go

## ใช้งาน

ทุกฟังก์ชันที่เกี่ยวกับภาษีต้องรับ `ShopContext` เข้ามา — ของเดิมอ่าน `DB.shop.vatRate`
จาก global ตรง ๆ ซึ่งทำให้เอกสารเก่าเปลี่ยนยอดตามเมื่อร้านแก้อัตราภาษี

```ts
import { recTotals, vatChain, bahttext } from '@drivegolight/core';

const ctx = { vatRate: 7 };

const t = recTotals({
  date: '2026-08-01',
  items: [
    { qty: 2, price: 1450 },                  // อะไหล่
    { qty: 1, price: 500, svc: true },        // ค่าแรง
  ],
  vatMode: 'ex',
  whtRate: 3,
}, ctx);

t.net      // 3400   มูลค่าก่อน VAT
t.vat      // 238
t.grand    // 3638   ยอดรวมทั้งสิ้น
t.whtBase  // 500    หัก ณ ที่จ่ายคิดจากค่าแรงเท่านั้น
t.wht      // 15
t.payable  // 3623   ยอดที่ลูกค้าจ่ายจริง

bahttext(t.payable)   // 'สามพันหกร้อยยี่สิบสามบาทถ้วน'
```


มีสองชุดที่ต้องมีคู่กันเสมอ

**1. `differential.test.ts` — เทียบกับโปรแกรมเดิม**

`test/extract-legacy.mjs` ดึงฟังก์ชันคำนวณ 29 ตัวออกจาก `drivegolight.html` แบบคำต่อคำ
(brace matching ไม่ใช่ regex เดา) แล้วห่อเป็นโมดูลให้เทสต์เรียกได้ จากนั้นสุ่มเอกสาร
4,000 ใบที่อัตราภาษี 4 แบบ แล้วเทียบผลทุกฟิลด์ว่าตรงกันเป๊ะ

`pretest` สร้างไฟล์นี้ใหม่ทุกครั้งก่อนรันเทสต์ ถ้าใครไปแก้ `drivegolight.html`
แล้วสูตรเปลี่ยน เทสต์จะแดงทันที

ชุดนี้คือหลักประกันว่าลูกค้าที่ย้ายจากไฟล์ HTML มาขึ้นเว็บจะเห็นยอดเท่าเดิมทุกบาท
**ถ้าแดง อย่าไปแก้ค่าที่คาดหวัง — กลับไปดูว่าพอร์ตสูตรผิดตรงไหน**

**2. `totals.test.ts` / `vat.test.ts` / `bahttext.test.ts` — เคสที่คิดเลขด้วยมือ**

ชุด differential บอกได้แค่ว่า "เหมือนของเดิม" ไม่ได้บอกว่า "ถูกต้อง"
ชุดนี้จึงเขียนเคสที่ตรวจสอบด้วยมือได้ เช่น เครดิตภาษีซื้อยกข้ามสามเดือน
หรือส่วนลดที่ต้องเฉลี่ยลงค่าแรงตามสัดส่วนก่อนคำนวณภาษีหัก ณ ที่จ่าย

## พฤติกรรมที่ยกมาจากของเดิมโดยตั้งใจ

ทั้งสามข้อนี้พอร์ตมาแบบตรงตัวเพื่อให้ยอดตรงกับเอกสารที่ลูกค้าออกไปแล้ว
ไม่ใช่เพราะมันเป็นวิธีที่ดีที่สุด

1. **ลำดับการปัดของภาษีหัก ณ ที่จ่าย** — `Math.round(base * rate) / 100`
   ไม่ใช่ `round2(base * rate / 100)` ผลต่างกันในบางเคส
   มีเทสต์ mutation ยืนยันว่าถ้าเปลี่ยนลำดับนี้ ชุด differential จะจับได้

2. **`sub` / `disc` / `base` ไม่ปัดทศนิยม** ปัดเฉพาะ `net` / `vat` / `grand`

3. **ใช้ float ไม่ใช่ decimal** — `Math.round(x*100)/100` ปัดเศษครึ่งสตางค์พอดีลง
   (เช่น 1.005 → 1.00) เพราะ float เก็บ 1.005 เป็น 1.00499...
   ในทางปฏิบัติแทบไม่มีผล แต่ถ้าวันหนึ่งจะย้ายไป decimal ทั้งระบบ
   ต้องตัดสินใจก่อนว่าเอกสารเก่าจะเปลี่ยนยอดตามหรือไม่

ฝั่งฐานข้อมูลเก็บเป็น `numeric` อยู่แล้ว (ดู `db/001_init.sql`) ค่าที่คำนวณเสร็จ
จึงถูกเก็บแบบไม่มีความคลาดเคลื่อนเพิ่ม
