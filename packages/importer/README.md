# @drivegolight/importer

นำเข้าไฟล์สำรองข้อมูล JSON ของ DriveGoLight! รุ่น HTML (`drivegolight-backup-*.json`)
เข้า Postgres ตามสคีมาใน [`db/001_init.sql`](../../db/001_init.sql)

## ใช้จากบรรทัดคำสั่ง

ตรวจไฟล์ก่อนโดยไม่เขียนอะไรลงฐานข้อมูล

```bash
node packages/importer/dist/cli.js ./drivegolight-backup-2026-08-28.json --dry-run
```

นำเข้าจริง

```bash
node packages/importer/dist/cli.js ./drivegolight-backup-2026-08-28.json --url=postgresql://user:pass@host:5432/dgl
```

| ตัวเลือก | ความหมาย |
|---|---|
| `--url=` | connection string (ไม่ใส่ก็ใช้ `DATABASE_URL`) |
| `--name=` | ชื่ออู่ (ไม่ใส่ก็ใช้ `shop.name` จากไฟล์) |
| `--opening-date=` | วันที่ลงยอดสต๊อกยกมา (ค่าตั้งต้น = วันนี้) |
| `--dry-run` | ตรวจไฟล์อย่างเดียว ไม่เขียนฐานข้อมูล |

## ใช้จากโค้ด

```ts
import { importBackup } from '@drivegolight/importer';

const result = await importBackup(client, JSON.parse(fileContents), {
  tenantName: 'อู่ ช่างเอ ออโต้เซอร์วิส',
});

result.tenantId    // uuid ของอู่ที่สร้างใหม่
result.counts      // จำนวนแถวที่เขียนแยกตามตาราง
result.warnings    // เรื่องที่ต้องบอกลูกค้า
```

## หลักการที่ยึด

1. **ทรานแซกชันเดียว** — ล้มที่ไหนก็ rollback หมด ไม่มีข้อมูลครึ่ง ๆ กลาง ๆ ค้างในฐานข้อมูล

2. **ยอดเงินคำนวณใหม่ ไม่ก๊อปมา** — ไฟล์เดิมไม่ได้เก็บยอดไว้เลย คำนวณสดตอนแสดงผลทุกครั้ง
   ตัวนำเข้าจึงเรียก [`@drivegolight/core`](../core) คำนวณให้ตรงกับที่โปรแกรมเดิมแสดงทุกบาท

3. **`legacy_id` ทุกตาราง** — เก็บ id เดิมจากไฟล์ไว้ ตามรอยกลับไปหาต้นทางได้
   และทำให้เทียบยอดกับโปรแกรมเดิมทีละใบได้

4. **สต๊อกลงเป็นรายการยกมาก้อนเดียว** — `products.qty` ของไฟล์เดิมเป็นยอดสะสมที่ผ่านการบวกลบ
   จากใบซื้อและใบเสร็จมาแล้ว ถ้าลงประวัติเก่าเพิ่มด้วยยอดจะกลายเป็นสองเท่า

5. **ไม่นำรหัสผ่านเดิมเข้ามา** — ไฟล์เดิมเก็บทั้ง `users[].pass` และ `shop.ownerPass`
   เป็นข้อความธรรมดา ทุกคนต้องตั้งรหัสใหม่ และเจ้าของต้องสมัครบัญชีเอง

## การแปลงไฟล์รุ่นเก่า

[`normalize.ts`](src/normalize.ts) ทำสิ่งเดียวกับที่ `loadDB()` ของโปรแกรมเดิมทำทุกครั้งที่เปิดไฟล์
— เติมฟิลด์ที่รุ่นหลังเพิ่มเข้ามา ย้าย `vendors[]` เข้า `customers` แปลงสิทธิ์ผู้ใช้รุ่นเก่า ฯลฯ

ข้ามขั้นนี้ไม่ได้ ไฟล์ของลูกค้าที่ใช้โปรแกรมมาหลายรุ่นจะพังกลางทาง
หรือแย่กว่านั้นคือนำเข้าสำเร็จแต่ข้อมูลผิดเงียบ ๆ

## เรื่องที่ importer ตัดสินใจให้เอง (แล้วเตือนผ่าน `warnings`)

| เจอ | ทำอะไร |
|---|---|
| รหัสสินค้าซ้ำ | เติมเลขต่อท้าย (ทะเบียนเดิมไม่บังคับไม่ซ้ำ ตารางใหม่บังคับ) |
| รหัสผู้ติดต่อซ้ำ หรือว่าง | เติมเลขต่อท้าย / ออกรหัส `CUS-` `VEN-` ให้ใหม่ |
| **เลขที่เอกสารซ้ำ** | เติมเลขต่อท้ายจนไม่ชน — ไม่ทิ้งเอกสารใบไหน |
| **เลขที่เอกสารว่าง** | ออกเลขให้ใหม่ `{ชนิด}-นำเข้า-0001` |
| ผู้ติดต่อไม่มีชื่อ | ใส่ `ไม่ระบุชื่อ (รหัส)` (ตารางใหม่บังคับว่าต้องมีชื่อ) |
| เลขผู้เสียภาษีไม่ครบ 13 หลัก | **เก็บค่าเดิมไว้** แล้วเตือน — ไม่ลบสิ่งที่ผู้ใช้กรอกทิ้ง กู้ไม่ได้ |
| IV/IVT ที่โหมดภาษีขัดกับชนิดเอกสาร | แก้ให้ตรงตามชนิด (เหมือน `enforceVat()` เดิม) |
| `assetLife` ติดมากับหมวดที่ไม่ใช่สินทรัพย์ | ไม่บันทึก (ตารางมี CHECK กำกับ) |
| รายการอ้างสินค้าที่ถูกลบไปแล้ว | เก็บเป็นรายการไม่ผูกทะเบียน ชื่อกับราคายังอยู่ครบ |
| รายการชื่อว่าง | ใส่ `(ไม่ระบุชื่อรายการ)` |
| ยอดชำระ 0 หรือติดลบ | ข้าม |
| ระดับราคาไม่ถูกต้อง | ใช้ A |

## ⚠ ตั้งค่า pg ก่อนใช้ในแอปจริง

Postgres คืนคอลัมน์ `date` มาเป็น JS `Date` ที่เที่ยงคืนตามเวลาเครื่อง
ถ้าเผลอเรียก `.toISOString()` ต่อ จะได้วันที่**ก่อนหน้า 1 วันเสมอ**ในเขตเวลาไทย (UTC+7)
วันครบกำหนดชำระและวันที่บนเอกสารจะเพี้ยนทั้งระบบ

```ts
import pg from 'pg';
pg.types.setTypeParser(1082, (v) => v);   // date → สตริง 'YYYY-MM-DD'
```

เป็นบั๊กเดียวกับที่โปรแกรมรุ่นเดิมเคยเจอ (ดูคอมเมนต์เหนือ `iso()` ใน `legacy/`)
ซึ่งเป็นเหตุผลที่ของเดิมไม่ยอมใช้ `toISOString()` เลย

## เทสต์

ต้องมี Postgres จริง ถ้าไม่ตั้ง `DATABASE_URL` เทสต์จะข้ามไปทั้งชุด

```bash
docker run -d --name dgl_pg -e POSTGRES_PASSWORD=x -e POSTGRES_DB=dgl -p 5433:5432 postgres:16-alpine
```

```bash
DATABASE_URL=postgresql://postgres:x@localhost:5433/dgl npm test -w @drivegolight/importer
```

มีสองไฟล์

**`import.test.ts`** — นำเข้าไฟล์ตัวอย่างจริง (เอกสาร 734 ใบ) แล้วอ่านกลับมาเทียบ

- ยอดทุกช่องของเอกสารทุกใบ เทียบกับที่ `@drivegolight/core` คำนวณจากไฟล์
- ยอดลูกหนี้คงค้างรวม · ภาษีขายรายเดือน · ต้นทุนขายและค่าใช้จ่ายดำเนินงานในงบกำไรขาดทุน
- สายเอกสาร ใบเสนอราคา → ใบส่งมอบ → ใบเสร็จ ผูกครบ
- ยอดสต๊อกคงเหลือตรงกับ `products.qty` ทุกตัว
- เลขที่เอกสารถัดไปไม่ซ้ำกับที่ออกไปแล้ว
- นำเข้าไฟล์เดิมซ้ำเป็นอู่ใหม่ได้ และแต่ละอู่มองไม่เห็นข้อมูลกัน (RLS)
- ไฟล์โครงสร้างผิดถูกปฏิเสธโดยไม่ทิ้งข้อมูลค้าง

**`hard-cases.test.ts`** — ไฟล์ที่จงใจสร้างให้โหด เพราะชุดจาก `seedDemo()` สะอาดเกินไป
จนโค้ดหลายเส้นทางไม่เคยถูกรันเลย ([`hard-cases.ts`](test/hard-cases.ts) เป็นตัวสร้าง)

- ไฟล์จากโปรแกรมรุ่นเก่าสุด — ไม่มี `kind` · มี `vendors[]` แยก · สิทธิ์ผู้ใช้แบบเก่า ·
  `terms:'cash'` · รถไม่มีเลขเครื่อง · ไม่มีหมวดหมู่ · ตัวนับเลขที่ขาดคีย์
- เอกสารที่ราคารวม VAT แล้ว (`vatMode:'in'`) รวมถึงฐานหัก ณ ที่จ่ายที่ต้องถอด VAT ก่อน
- ข้อมูลสกปรก — รหัสซ้ำ · ชื่อว่าง · เลขภาษีเพี้ยน · สต๊อกติดลบ · ตัวเลขเป็นข้อความมีคอมมา ·
  ยอดชำระติดลบ · อ้างสินค้าที่ถูกลบ · `assetLife` ผิดหมวด · ลิขสิทธิ์ที่ยังไม่หมดอายุ
- ชนิดเอกสารขัดกับโหมดภาษี
- เลขที่เอกสารซ้ำและว่าง
- เอกสาร 2,700 ใบ มากพอให้ตัวแทรกต้องแบ่งก้อน — พิสูจน์ว่าสายเอกสารยังผูกครบข้ามก้อน
- ไฟล์ว่างเปล่าของอู่ที่ยังไม่มีข้อมูล

ตัวนำเข้าในเทสต์ต่อฐานข้อมูลด้วย role ธรรมดา ไม่ใช่ superuser เพื่อให้ RLS ทำงานจริง
เหมือนตอนใช้งาน — superuser จะข้าม RLS ทั้งหมดและทำให้เทสต์ผ่านแบบหลอก ๆ

เทสต์ทั้งสองไฟล์ล้างสคีมาใหม่ตอนเริ่ม จึงตั้ง `fileParallelism: false` ไว้ให้รันทีละไฟล์
